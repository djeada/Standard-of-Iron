# Ultra / Full-LOD Performance Plan

## Objective

Make real campaign play consistently fast with the `Ultra` graphics profile and the
highest-detail creature geometry everywhere, without changing gameplay results or
silently lowering visual quality.

The target contract is:

- Full creature geometry and every authored attachment in color and directional-shadow
  passes.
- Ultra lighting, four cascaded shadows, weather, particles, post-processing, terrain,
  foliage, and water remain enabled.
- No billboards, reduced creature meshes, dropped attachments, reduced shadow geometry,
  animation skipping, or simulation shortcuts in the measured Full-LOD path.
- No geometry generation, skin-frame baking, asset decoding, shader compilation, heap
  growth, or OpenGL resource creation after a mission becomes playable.
- Deterministic movement, combat, replays, saves, and AI decisions remain unchanged.

“Build-time mesh construction” means that topology, vertices, indices, attachment-set
composition, skinning metadata, mesh optimization, and snapshot frame streams are
generated by asset tools. The player’s GPU buffers cannot literally be made at build
time; they must be uploaded on the target GPU. That upload must be bulk, bounded, and
complete behind the loading screen, before the first playable frame.

## Evidence from the first campaign missions

The current 10-second mission runs used a `RelWithDebInfo` build and the Medium preset,
after the built-in two-second warm-up. They are diagnostic evidence, not the final Ultra
baseline. Another game process was already using the GPU, so absolute GPU timings must
be re-measured on an otherwise idle desktop.

| Mission            | Average FPS | Render average | Render p95 | Update average | GPU color average |
| ------------------ | ----------: | -------------: | ---------: | -------------: | ----------------: |
| Crossing the Rhône |       57.09 |        7.32 ms |   17.54 ms |        3.40 ms |           3.18 ms |
| Crossing the Alps  |       29.80 |       21.54 ms |   69.79 ms |       14.05 ms |           7.62 ms |
| Battle of Ticino   |       58.89 |        6.17 ms |   18.04 ms |        1.45 ms |           3.57 ms |

Steady-state `perf` samples from Crossing the Alps exposed work that should not be in a
playable frame:

- `Render::GL::bake_snapshot_vertices`: 6.95% of the sampled render/core profile.
- `Render::GL::RiggedMesh::RiggedMesh`: 5.96% of the sampled render/core profile.
- `Walkability::can_stand_on`: 10.10% of the sampled simulation/atom profile.
- `Walkability::nearest_standable`: 5.49% of the sampled simulation/atom profile.
- `Pathfinding::is_world_position_walkable`: 1.60% and
  `Pathfinding::find_path_internal`: 1.15% of the sampled core profile.
- Every mission reported forbidden `snapshot_mesh_bake` and/or
  `creature_submit_miss` operations after prewarm.

Those percentages come from different sampled views and are not additive. They do show
three concrete problems: the preload catalog is incomplete, runtime cache misses still
construct GPU-facing mesh objects, and standability/corridor validation repeats too much
floating-point and terrain work.

The existing massed-battle documentation also establishes the Full-LOD GPU ceiling:
2,000 rendered soldiers currently cost about 37–41 ms on the reference RTX 5060, split
roughly into 15–16 ms of shadows and 22–24 ms of color. The workload is vertex-bound:
about 4,340 rigged instances process roughly 15,000 vertices in color and again across
the shadow cascades. Existing batching already reduces those to about 25 actual indexed
draws per pass, so another draw-call-only pass will not solve that workload.

## Performance gates

All frame gates exclude loading and a declared warm-up interval, run at 1920×1080, and
require `Ultra`, Full LOD, real shadows, GPU timers, an active unlocked desktop, and no
other game process. Report p50, p95, p99, maximum, CPU thread time, each simulation
system, each render phase, GPU shadow/color time, queue wait, allocations, and cache
events. Archive raw JSON and `perf` data, not only summaries.

### Release gates

- [ ] Each of the first three campaign missions reaches frame p50 <= 12.0 ms,
      p95 <= 16.67 ms, p99 <= 20.0 ms, and post-warm-up max <= 33.3 ms.
- [ ] `campaign_scale_battle` reaches p95 <= 16.67 ms and p99 <= 20.0 ms.
- [ ] Simulation update is <= 2.0 ms average and <= 4.0 ms p95 in those missions.
- [ ] Navigation is <= 0.25 ms average and <= 1.0 ms p95 per simulation tick, including
      standability, corridor planning, route validation, and dirty-region maintenance.
- [ ] Render-thread CPU submission is <= 3.0 ms p95 at campaign scale.
- [ ] GPU shadow plus color is <= 12.0 ms p95 at campaign scale.
- [ ] No post-load frame contains a runtime mesh/snapshot bake, geometry assembly,
      texture/audio decode, shader compile/link, GL object creation, or unbounded allocation.
- [ ] No post-load frame logs a runtime bake or missing-preloaded-asset violation.
- [ ] Deterministic replay digests and movement-quality gates match the accepted baseline.

### Scale gates

- [ ] `massed_battle_250` (500 visible soldiers) holds p95 <= 16.67 ms.
- [ ] `massed_battle_500` (1,000 visible soldiers) holds p95 <= 25.0 ms.
- [ ] `massed_battle_1000` (2,000 visible soldiers) first reaches p95 <= 33.3 ms with no
      frames above 50 ms; the stretch goal is p95 <= 16.67 ms.
- [ ] Scale is smooth: no cache-capacity cliff, fallback renderer, or multi-frame queue
      stall appears when moving between the 500, 1,000, 2,000, and 4,000-soldier fixtures.

The 2,000-soldier 60 FPS figure is a stretch target, not a promise to hide quality loss.
It requires reducing exact vertex work or sharing exact skinned poses; it must not be met
by changing the Full-LOD contract.

### Measured findings from the Phase 0 instrumentation

Recorded 31 Aug 2026 at `6a6fca63`, RelWithDebInfo, Ultra, Battle of Ticino. Full detail
and caveats in `docs/PERFORMANCE_INSTRUMENTATION.md`.

- One playable mission performs **869 asset operations after the load barrier**: 638 GL
  buffer creations, 216 vertex arrays, 4 texture creations, 4 shader compiles, 2 program
  links, 1 rigged-mesh bake, 2 `RiggedMesh` constructions, 28.8 MB uploaded. The existing
  guard only ever logged the two bake operations; the GL object creation was invisible.
- **The barrier is not reliably reached.** A second run of the same binary and mission
  produced identical totals but never latched `runtime_bake_forbidden` at all, because
  the latch is the tail of a best-effort background prewarm. Post-load work is therefore
  unmeasurable in some runs. This is the concrete case for 1.4.
- Navigation asks the grid **~2,120 position tests per soldier per tick**, flat to 0.4%
  across 1k/2k/5k units. Scale-invariant, so it gates on a shared runner; it is the
  number Phase 2 exists to collapse.
- Navigation is _not_ the cost in Ticino: 0.005 ms p95 per tick against a 1.0 ms budget.
  Crossing the Alps, where the plan's evidence puts the cost, has not been measured with
  these counters yet.
- `renderer_to_first_playable_frame_seconds` is 12.24 s, much of it audio resampling and
  mastering at startup (Phase 6).

Battle of Zama, 600 measured seconds, 69,191 frames over 48,830 ticks (800x800 map, four
AI opponents, 1,050-troop cap). Timings are directional -- the box was busy -- counters
are exact:

- **A navigation rebuild is a ~0.9 s freeze.** _(fixed: a gate state change marked the
  whole grid dirty; it now marks only the blocker regions.)_ Worst frame 933.9 ms with `update_ms`
  922.7 ms in the same frame. `grid_rebuilds` 5 and `dirty_cells_rebuilt` 2,560,343 =
  4.0x the 640,000-cell map, so four were whole-map rebuilds inside one tick. This is the
  concrete case for 2.2's dirty-tile rebuild.
- **3.9 billion position tests** in ten minutes (80,023 per tick); 27.1M cells expanded;
  route cache 9,146 hits / 3,922 misses. Navigation still fits its per-tick budget
  (0.02 ms p95 vs 1.0 ms) because each query is cheap -- the count is the problem, and it
  is why a topology change costs a second.
- **The load barrier did not latch for the third run running.** Ten minutes rules out
  "the run ended too early". 260 rigged bakes, 270 mesh constructions, 516 MB of vertex
  bytes, 240 shader compiles and 869 GL buffers are therefore unattributable to loading or
  to play. Until 1.4 lands, no run can establish the no-post-load-bake property.

## Phase 1 — Eliminate runtime geometry construction

The base creature bodies are already generated by `tools/bpat_baker` into `.bprm` files.
The remaining problem is that runtime code still copies blob views into vectors and calls
`RiggedMesh` constructors, while arbitrary bake-attachment sets and many snapshot keys
still fall back to CPU geometry work. “Prewarm” merely moves that work earlier and is
currently incomplete; it is not the final architecture.

### 1.1 Make render permutations finite and content-addressed

- [ ] Introduce a compiled render-asset manifest generated from every shipped campaign,
      mission, wave/reinforcement definition, faction roster, archetype, commander, wildlife
      spawn, building producer, equipment set, and save-compatible visual ID.
- [ ] Replace pointer-based or incidental cache identity with stable IDs. A key must
      include schema/tool version, creature/species, body graph, LOD, skin species, authored
      attachment-set ID, material/role layout, and source content hashes.
- [ ] Make attachment sets authored catalog entries instead of arbitrary runtime arrays.
      Validate duplicate IDs, non-canonical ordering, invalid sockets, and accidental
      Cartesian-product growth.
- [ ] Avoid permutation explosion by keeping the body shared, baking each unique
      attachment mesh once, and composing authored attachment sets as compact references into
      shared vertex/index arenas. Do not duplicate the 14,888-vertex humanoid body per set.
- [ ] Have `tools/content_validator` fail the build when mission content can request a
      render key absent from the compiled manifest.
- [ ] Emit a human-readable manifest report listing every key, source owner, byte size,
      duplicate, and unreachable asset.

Primary touchpoints: `tools/bpat_baker/`, `tools/content_validator/`, creature manifests,
mission/campaign loaders, `render/template_prewarm_catalog.*`, and
`render/creature/assets/`.

### 1.2 Cook GPU-ready immutable assets

- [ ] Extend the creature baker, or add a focused render-asset cooker, to emit one
      versioned pack plus an index for bodies, authored attachment sets, indices, exact
      rigid/blended ranges, bounds, role metadata, and animation links.
- [ ] Store data in the exact runtime byte order, alignment, and packed vertex format so
      loading never rebuilds vertices, remaps indices, partitions ranges, or copies through
      temporary `std::vector`s.
- [ ] Bake all skin-atlas transforms and bind-dependent metadata. No runtime
      `palette × inverse_bind` work is allowed.
- [ ] Generate snapshot frame streams for every species/LOD that can use the snapshot
      path, not only the current subset of minimal wildlife `.bpsm` assets.
- [ ] For snapshot attachments, either bake the finite authored set into the snapshot
      stream or keep the attachment as its own pre-skinned stream. Never call
      `bake_snapshot_vertices` in the game executable.
- [ ] Optimize offline index order, vertex-cache locality, overdraw order, and duplicate
      vertices while preserving the exact accepted Full asset and skinning result.
- [ ] Produce deterministic output: identical source/tool versions must produce identical
      bytes and hashes on clean rebuilds.
- [ ] Add format versioning, checksums, bounds checks, and a clear stale/corrupt-asset
      diagnostic.
- [ ] Wire every generated output into CMake dependencies so an edit to part graphs,
      skeletons, attachments, materials, clips, or schemas rebuilds only affected artifacts.

Primary touchpoints: `tools/bpat_baker/main.cpp`, `tools/bpat_baker/CMakeLists.txt`,
`render/rigged_mesh_bake.*`, `render/creature/rigged_mesh_asset.*`,
`render/creature/snapshot_mesh_asset.*`, and creature runtime manifests.

### 1.3 Replace per-mesh objects with arena views

- [ ] Bulk-load or memory-map the compiled pack during mission loading.
- [ ] Upload vertices and indices into a small number of immutable GPU arenas, using a
      bounded staging buffer. Create all GL objects before the loading barrier ends.
- [ ] Replace owning runtime `RiggedMesh` instances for baked content with lightweight
      immutable views: buffer handle, vertex/index offset, counts, ranges, bounds, and asset
      ID.
- [ ] Remove the blob-to-`std::vector` copies at `render/rigged_mesh_cache.cpp:216-218`.
- [ ] Remove production calls to `bake_rigged_mesh` at
      `render/rigged_mesh_cache.cpp:225` and `:237`.
- [ ] Remove production calls to `bake_snapshot_vertices` at
      `render/snapshot_mesh_cache.cpp:166` and `:180`.
- [ ] Make `RiggedMeshCache` and `SnapshotMeshCache` lookup-only registries for shipped
      content. A miss reports the stable missing key; it never tries to repair itself in a
      frame.
- [ ] Keep CPU vertex/index copies only where a named editor or diagnostic feature proves
      it needs them. Otherwise release staging memory after upload.
- [ ] Upload species BPAT buffers and immutable render arenas once, then reference them by
      offsets from draw commands.

### 1.4 Make the loading barrier strict

- [ ] Replace best-effort prewarm with a manifest-backed load transaction that knows its
      total item/byte count and cannot declare completion while a required asset is missing.
- [ ] Split loading into CPU I/O/decompression, validated staging, render-thread upload,
      and fence completion. Show progress from actual completed bytes/items.
- [ ] Set `runtime_bake_forbidden` before the first world render, not after a heuristic
      prewarm timer.
- [ ] In tests and developer builds, abort immediately on a post-barrier bake, GL object
      creation, or missing key. In release builds, show a preloaded diagnostic placeholder
      and telemetry rather than baking or stalling.
- [ ] Add a zero-budget mode that disables all runtime fallback code and run it in CI.
- [ ] Delete runtime bake code from production link targets once editor/tool callers are
      separated into `creature_bake`; keeping dead fallback code makes regressions easy.

### 1.5 Mods and development content

- [ ] Give mods and editor content an explicit offline “cook assets” command and a
      content-addressed local cache.
- [ ] Run that cooker before launching a match; never compile a mod’s geometry on the
      render thread.
- [ ] Invalidate only entries whose source or tool hash changed.
- [ ] Keep shipped campaign completeness a build error even if the development cooker is
      available.

## Phase 2 — Make standability and pathfinding ultra-cheap

The runtime should search only when topology or an order genuinely changes. A marching
formation should follow one shared route without asking A* or terrain services questions
for every member on every tick.

### 2.1 Compile static navigation with each map

- [ ] Add a versioned navigation artifact to the map/content build. Include grid origin,
      dimensions, cell size, terrain class, Light/Heavy passability bitsets, quantized ground
      height, slope/bridge/entrance flags, clearance or distance-to-obstacle fields, connected
      components, and a hierarchical sector/portal graph.
- [ ] Build static standability classes for the finite body-clearance buckets used by the
      game. `can_stand_on` should normally be one bounds check plus indexed bit/byte reads.
- [ ] Precompute nearest-valid guidance per passability/clearance class, or use a compact
      ring-offset table over the O(1) bitsets. `nearest_standable` must not repeatedly sample
      terrain height, slope, and world-position walkability.
- [ ] Precompute sector entrances and intra-sector costs/paths for hierarchical planning.
- [ ] Validate campaign spawn points, objectives, gates, bridges, production exits, and
      scripted destinations against the compiled graph. Fail content validation on unintended
      disconnected regions.
- [ ] Hash terrain topology and reject stale navigation artifacts at load.

Primary touchpoints: map build/validation tools, `game/systems/pathfinding.*`,
`game/systems/walkability.*`, terrain services, and map resource staging.

### 2.2 Separate static data from dynamic overlays

- [ ] Keep the compiled static grid immutable and lock-free for readers.
- [ ] Represent buildings, gates, destructibles, and harvested resources in sparse tiled
      overlays with per-tile revisions. Unit occupancy stays out of the global navigation
      grid; local avoidance already owns that dynamic problem.
- [ ] Rebuild only dirty tiles plus the exact clearance halo, component links, and affected
      portals. Never clear the whole path cache for a distant local edit.
- [ ] Replace one global navigation revision with static version plus per-tile/sector
      revisions so unaffected cached corridors survive.
- [ ] Publish rebuilt overlay snapshots atomically at a deterministic tick boundary. Hot
      readers take no global `shared_mutex`.
- [ ] Add dirty-work budgets measured in cells/portals rather than wall time, with backlog
      age and overflow counters.

### 2.3 Make hot queries integer and branch-light

- [ ] Add grid-space APIs that accept packed cell IDs and clearance classes. Keep
      `QVector3D`, `round`, `floor`, `ceil`, `hypot`, and repeated world/grid conversion out of
      inner route-validation loops.
- [ ] Replace the neighborhood scan in
      `Pathfinding::is_world_position_walkable` with a distance/clearance-field lookup plus a
      precise boundary test only for the rare sub-cell edge case.
- [ ] Replace clearance segment sampling every 0.2–0.35 m with integer grid traversal plus
      clearance-field reads. Preserve the same collision semantics at corners.
- [ ] Expose unchecked row/span/bitset operations for code that already proved bounds;
      retain checked public entry points.
- [ ] Cache ground height in the compiled cell and perform one final terrain interpolation
      only when a world-space waypoint is emitted.
- [ ] Batch lane-validity probes and use word-at-a-time bitset tests where a corridor tests
      many neighboring cells.

### 2.4 Search hierarchically and share routes

- [ ] Plan long routes over the precomputed sector/portal graph, then refine only the
      sectors touched by the selected corridor. Keep exact local A* for short routes and
      topology-repair fallbacks.
- [ ] Key corridor caches by start sector/portal, goal sector/goal bucket, passability,
      clearance class, and only the revisions intersecting that corridor.
- [ ] Give each group order one immutable, reference-counted route handle. Members store a
      lane offset and progress index, not copied waypoint vectors.
- [ ] Coalesce same-tick and nearby orders before searching. One army destination should
      not generate one path per selected unit.
- [ ] Add destination flow fields for large groups converging on the same local objective
      when measurement shows lane corridors are insufficient.
- [ ] Revalidate a route only when it enters a changed tile/sector, crosses a portal,
      becomes locally blocked, or receives a new order. Do not probe every member every tick.
- [ ] Keep individual A* as a bounded recovery path only. Count every fallback and make a
      sustained fallback rate fail the benchmark.
- [ ] Preserve the existing rule that local unit avoidance/body contact uses
      `WorldSpatialIndex`, not navigation-grid occupancy.

Primary touchpoints: `game/systems/route_corridor_planner.*`,
`movement_orders.cpp`, `movement_system.*`, `route_follow_system.*`,
`unit_traversal_layout_system.*`, and formation registry/planner code.

### 2.5 Bound the remaining exact search

- [ ] Profile binary-heap A* against an integer bucket/radix queue and Jump Point Search
      on representative maps. Keep only an option that preserves weighted costs, clearance,
      forests, corner rules, and path quality.
- [ ] Pack search state into cache-friendly arrays and precompute neighbor masks/costs per
      cell and passability class.
- [ ] Retain generation-stamped scratch buffers, but allocate one fixed-capacity context
      per deterministic search lane at load; no search-time allocation or hash growth.
- [ ] Replace the 256-entry clear-all exact-path cache with bounded LRU/clock storage or
      sector-corridor caches that invalidate locally.
- [ ] Schedule recovery searches using a fixed node-expansion budget, request sequence,
      and deterministic commit order. Do not use wall-clock budgets or generic asynchronous
      completion timing that can change replay results across machines.
- [ ] Keep the existing pending-request cap as a final safety net, but report queue age,
      cancellations, duplicates, and deadline misses. “Eight requests per tick” is not proof
      of cheapness if each request is still large.

### Phase 2 acceptance

- [ ] At least 99% of formation members reuse a group corridor in campaign and massed
      battle workloads.
- [ ] Steady marching ticks execute zero A* searches and zero nearest-standable searches.
- [ ] New group route p95 is <= 0.50 ms; local recovery p95 is <= 0.20 ms on the reference
      CPU, with cells-expanded budgets recorded alongside time.
- [ ] `can_stand_on` and `nearest_standable` together consume <= 0.10 ms p95 per tick in
      Crossing the Alps.
- [ ] A local building/gate/resource change touches only intersecting tiles and causes no
      unrelated corridor invalidation or frame above budget.
- [ ] No navigation query waits on a global mutex in the steady state.
- [ ] Existing pathfinding, tight-gap, river-bank, world-prop, formation movement, route,
      and movement-quality tests pass with identical accepted outcomes.
- [ ] Replay digests match across repeated runs and different worker counts.

Exit gate: navigation work scales primarily with changed topology and group orders, not
with the number of soldiers multiplied by simulation ticks.

## Phase 4 — Reduce exact Full-LOD GPU work

Draw batching, exact indexed instancing, resident BPAT palettes, and the bounded two-frame
GPU queue already exist. Preserve them. The remaining massed-battle problem is vertex
work, not the number of API draw calls.

### 4.1 Pack and optimize the Full asset offline

- [ ] Produce a vertex accounting report by body part and attachment: source triangles,
      vertices after seams, rigid/blended vertices, bytes, cache miss ratio, and shadow/color
      shader invocations.
- [ ] Weld truly identical vertices, remove unreachable/degenerate geometry, optimize
      index order, and reduce accidental primitive tessellation where image/pose tests prove
      no visible loss. The optimized asset becomes the one Full asset used in both passes;
      this is not runtime LOD.
- [ ] Evaluate packed positions, octahedral normals, compact UVs, integer bone IDs,
      normalized weights, and compact role IDs. Decode in shaders and retain a precise path
      for assets that exceed quantization bounds.
- [ ] Partition rigid and blended ranges in the cooker and encode the one-bone rigid path
      directly; do not rediscover ranges at load.
- [ ] Measure every format change with GPU timestamps and bandwidth/occupancy tools. Keep
      it only if color, shadow, and total frame time improve on campaign and 2,000-soldier
      workloads.
- [ ] Require image comparisons at near, mid, silhouette, animation-extreme, attachment,
      and four-cascade shadow views before accepting topology/packing changes.

### 4.2 Share exact skinned poses instead of skinning every instance

- [ ] Count distinct pose keys versus rendered instances per frame for march and melee.
      Include mesh, exact BPAT frames, interpolation buckets, layered blend/overlay key, and
      any state that changes vertex output.
- [ ] Prototype a bounded GPU pose cache that skins one vertex stream per distinct pose
      key, then instances world transforms/material roles from that shared exact stream in
      color and shadows.
- [ ] Size the cache by distinct poses, not soldiers. Reuse the existing fixed
      blend/selection buckets only where they already define the accepted animation result;
      do not add coarser animation quantization.
- [ ] Reuse resident results across both passes and, when keys persist, across frames.
- [ ] Fall back to the current exact indexed skinning path when pose reuse is too low or a
      bounded cache is full. Never fall back to CPU snapshot baking.
- [ ] Evaluate build-time pre-skinned BPAT streams only if compressed storage plus upload
      beats the on-GPU unique-pose cache. Record pack size, load bytes, residency, and GPU
      time before choosing.
- [ ] Cap pose-cache compute, bytes written, residency, and eviction work. Expose all four
      as frame-profile counters.

This differs from the rejected per-instance pre-skin experiment: that path wrote roughly
544 MB every frame for 2,000 soldiers. A viable design must write once per reused pose,
not once per instance.

### 4.3 Tune exact shaders and pass scheduling

- [ ] Capture vendor GPU profiles for color and each shadow cascade after vertex packing
      and pose sharing, then optimize the measured instruction/memory bottleneck.
- [ ] Keep exact frustum/cascade culling and avoid submitting an instance to cascades it
      cannot affect. Verify culling does not alter the accepted shadow image.
- [ ] Remove redundant palette/instance/vertex fetches between rigid and blended paths.
- [ ] Keep persistent immutable frame streams bounded and fence-safe; no orphan/grow event
      may occur after load.
- [ ] Bake shader source preprocessing/validation offline. Cache driver-specific program
      binaries by GPU vendor/device/driver and shader hash during the loading screen; never
      trust a cache across incompatible drivers.
- [ ] Measure frame overlap and the two-frame queue. Reduce waits through real GPU work
      reduction, not by allowing an unbounded queue that hides latency.

### Phase 4 acceptance

- [ ] Full body/attachment vertex bytes and vertex-shader invocations are reduced with an
      accompanying image/pose equivalence report.
- [ ] GPU shadow plus color meets the campaign release gate.
- [ ] `massed_battle_1000` meets the 33.3 ms p95 scale gate before pursuing the 16.67 ms
      stretch gate.
- [ ] No reduced shadow mesh, dropped attachment, temporal skip, animation approximation,
      or lower LOD appears in reports or captures.

## Phase 5 — Optimize the rest of Ultra rendering

- [ ] Profile terrain, foliage, buildings, particles, water, weather, post-processing,
      UI composition, and each shadow category independently in the real campaign camera
      paths.
- [ ] Cook static world geometry into spatial chunks with immutable vertex/index arenas
      and indirect draw records. Rebuild only editor/dynamic chunks, never static campaign
      scenery in a frame.
- [ ] Use hierarchical visibility/occlusion data for terrain and static chunks where it
      lowers measured GPU work. Never cull potentially visible gameplay silhouettes.
- [ ] Instance repeated vegetation, rocks, props, and buildings by material/mesh while
      preserving Ultra density and shadows.
- [ ] Generate texture mipmaps, compression/transcoding payloads, terrain blend data,
      foliage placements, and material tables offline. Upload them in bounded loading jobs.
- [ ] Preallocate weather/particle pools and GPU buffers to the Ultra maximum. Do not grow
      them during a storm or mission event.
- [ ] Reuse shadow maps and static shadow data only when camera/light/object revisions
      prove the result remains exact. Dynamic creatures continue to cast Full shadows.
- [ ] Eliminate redundant full-screen copies and state transitions identified by GPU
      capture; keep post effects and output unchanged.
- [ ] Make render phase and logical/physical draw counters distinguish actual GPU calls
      from high-level commands so optimization targets the right layer.

Exit gate: non-creature Ultra features fit inside the remaining campaign GPU budget and
introduce no post-load allocation or compilation spike.

## Phase 6 — Loading, memory, and background work

- [ ] Define separate CPU staging, CPU resident, GPU static, GPU frame-stream, snapshot,
      pose-cache, texture, audio, and navigation budgets for Ultra.
- [ ] Remove duplicate CPU/GPU copies once immutable uploads complete. Current snapshot
      accounting assumes roughly two copies and defaults to 384 MB; the cooked path should
      make that duplication unnecessary for Full LOD.
- [ ] Pre-size hash tables, vectors, queues, frame streams, and descriptor tables from the
      compiled manifests. A match must not discover its capacity by reallocating.
- [ ] Use bounded worker queues for I/O/decompression and reserve the render thread for
      ordered uploads. Surface queue saturation rather than silently doing work inline.
- [ ] Use `tools/audio_master` outputs consistently and move decode/resample/mastering out
      of game startup/play. Prefetch required mission audio before play; stream long content
      from a bounded worker/ring without blocking simulation or rendering.
- [ ] Record peak RSS, resident GPU bytes, staging peak, upload volume, loading duration,
      and time-to-first-playable-frame for every benchmark.
- [ ] Add a low-memory failure path that reports which manifest budget failed before a
      match starts; do not evict/rebuild immutable creature assets mid-match.

Exit gate: loading is explicit and bounded, and steady play performs no asset work that
can be completed by the build or loading pipeline.

## Explicit non-goals and known dead ends

- [ ] Do not reintroduce per-instance pre-skinning that writes hundreds of megabytes per
      frame; the measured 544 MB/frame experiment was slower.
- [ ] Do not optimize the already-batched 2,000-soldier path as if 4,360 logical commands
      were 4,360 physical draws; it is about 25 indexed draws per pass.
- [ ] Do not use reduced creature or shadow meshes, billboards, missing attachments,
      fewer Ultra cascades, temporal soldier skips, or coarser animation to pass the gates.
- [ ] Do not put dynamic unit occupancy into the global navigation grid; use local
      avoidance and the shared spatial index.
- [ ] Do not move gameplay path decisions to nondeterministic GPU or wall-clock-scheduled
      jobs.
- [ ] Do not generate every theoretical attachment Cartesian product. Compile authored
      finite sets and share bodies/individual attachment geometry.
- [ ] Do not hide startup work behind a longer undocumented warm-up. Loading and warm-up
      must be separately reported and bounded.
- [ ] Do not accept an optimization from one unpaired run, a locked desktop, a different
      boot/driver, missing GPU timers, or a workload that is not actually Ultra/Full.
- [ ] Do not begin a broad ECS, renderer, or pathfinding rewrite without a counter showing
      the targeted work survives the earlier phases.
